Build journal · Vikash Kumar · Work in progress

Callmeter

A tool for admins of the ServiceNow® platform that traces each ServiceNow® Integration Hub transaction back to the flow that made it, and flags the transactions that bought nothing.

Started 13 Oct 2026 Current phase 1 · Build Spike result 8 of 8 transactions predicted Test lab 19 of 22 transactions bought nothing

The problem

Integration Hub counts a transaction when a flow calls an outside system, such as a REST call to another tool. In 2026 ServiceNow bundled Workflow Data Fabric Foundation, which includes Integration Hub, into every product tier edition, so more instances now run flows that spend from a yearly transaction allowance.

The Integration Hub Usage Dashboard shows those transactions by spoke, action, protocol and calling app scope, month by month. On my test instance, the usage table behind it records one row per action per month with a single count. What it can't say is which flow spent the transactions, whether the call worked, or whether the run that paid for it did anything useful. Admins on the ServiceNow Community describe the same gap: an instance shows "Overallocated" and there is no built-in way to find which flow is the heavy user.

What the tool will do

For each flow, show the transactions it spent, how many went to calls that failed, and how many went to runs that changed nothing, with a plain-language cause and a suggested fix. It reads through the standard REST Table API, only reads, and doesn't keep instance data.

How I found it

I wanted to build something real on the ServiceNow platform rather than write about it. The problem had to be useful and viable for real customers, whatever my own background, and I had to be able to prove it on a free Personal Developer Instance.

How I'm approaching the build

  • Predict, then check against the platform. Every test flow gets a written prediction before it runs. The proof is matching the platform's own numbers, not my own.
  • Small test lab. Each test flow shows one pattern and has a clear name: no call, one call, call before check, failing call. Details are in lab/.
  • Build next to the dashboard, not against it. The native dashboard already counts transactions. The tool adds the flow, the outcome and the fix.
  • Trust first. Read-only. Credentials stay in the admin's own environment. No instance data in the repo. For real use I recommend a separate read-only account set to Web Service Access Only.
  • How I work. I use an AI assistant (Claude) for research and coding. Problem choice, product decisions and trade-offs are mine, and each is recorded with its reasoning in the decision log.

Journal

15 Oct 2026 · Day 3, evening

One polling flow, and what native views show

Checked the native views by hand before claiming anything. The Integration Hub Usage Dashboard can be viewed by Overview, Spokes, or Protocols and Features, but not by flow. The FDIH Dashboard has an IH Usage tab, which showed 8 transactions this month split by action, and a Flow Executions tab, which lists runs with their state and calling source. The two tabs aren't joined: no run shows how many transactions it used. The same header showed 0 errored flow runs in the last 24 hours, a window that included the two IH-03 runs whose calls failed. Automation Center, whose Executions dashboard shows failed transactions by flow according to its documentation, isn't installed on a developer instance, so I couldn't test it.

Then I built the waste pattern customers describe most: polling. IH-05 runs every 5 minutes, makes the same GET call and does nothing with the result, the way a sync job polls when nothing has changed. I ran it for one hour.

Prediction: 12 runs and 12 calls. Result: 12 runs, exactly 5 minutes apart, 12 calls, all linked, all flagged as bought nothing. At that rate one polling flow makes about 8,640 calls in 30 days, or about 105,000 a year. A Community reply puts the current Starter allowance at 100,000 transactions a year. I haven't been able to confirm that figure, but if it's right, one small polling flow would use all of it.

Lab total so far: 22 transactions, 19 of them bought nothing. The lab is built to show patterns, so that ratio says nothing about real instances.

15 Oct 2026 · Day 3, morning

A flow that uses its call, and the first overlap

Added IH-04: the same GET call as IH-01, but the flow writes the response into the incident's work notes. To do that I had to add a Response Body output to the shared action first. Until then the response stayed inside the action and no flow could use it, which is part of why IH-01 wasted every call.

Prediction: 2 calls, both with an effect, 0 bought nothing. Result: exactly that. The lab now has 10 transactions: 1 useful from IH-02, 2 from IH-04, and 7 that bought nothing.

It also gave the first overlap. The two IH-04 runs started 14 seconds apart, and the first run's record was still being updated when the second run's call went out, so that call fitted inside both runs' time windows. The tool gives an overlapping call to the run that started most recently, which was right here. On a busy instance this will happen more often, so linking calls by their step, not just by time, is now on the list.

14 Oct 2026 · Day 2, night

7 of 8 transactions bought nothing, including my own baseline

Added a second check: did the run change anything? For each run, the tool reads the record history (sys_audit) for changes made by the flow's account on the run's own record while the run was going. Each run carries a link to the record that started it, so no guessing by time is needed for this part.

On IH-02 it found the one priority 1 run that wrote its work note, and the 2 runs that paid for a call and then stopped at the check. That is the pattern I built the flow to show.

It also flagged all 3 IH-01 runs. I had treated IH-01 as the healthy baseline, but it fetches data and never uses it, so every one of its transactions bought nothing. The tool was right and my lab was wrong. Real flows nearly always do something with a response, so next I'm adding a version of IH-01 that writes what it fetched into a work note.

Across the lab: 8 transactions, 2 on calls that failed, 5 on runs that changed nothing, 1 that did its job.

14 Oct 2026 · Day 2, evening

The ledger matches: 8 of 8

The usage table behind the Integration Hub Usage Dashboard updates in a batch, not live. Hours after the morning's runs it showed two rows: 6 transactions for the action IH Spike GET todo and 2 for IH Spike GET fail. My prediction, written before any flow ran, was 6 and 2.

Failed calls are billed. Both calls that returned HTTP 500 were counted as transactions.

The ledger is per action, not per flow. IH-01 and IH-02 use the same action, so their 6 transactions sit on one line. From the ledger alone there is no way to tell that 3 came from each flow, or that 2 of IH-02's 3 were spent on runs that did nothing.

14 Oct 2026 · Day 2, afternoon

A first tracer that links each call to its flow

Wrote a small Python script that reads two tables through the REST Table API: flow runs and the outbound HTTP log. It keeps only calls made by flow steps and links each one to the run whose time window contains it.

The first run failed with HTTP 401. This year's Basic Auth restriction only lets accounts with the snc_basic_auth_api_access role use basic authentication for the API, so the admin account on my test instance needed it. A real install should use its own read-only account instead.

Result: 10 runs, 8 calls, all 8 linked, none ambiguous. Per flow: IH-00 made 0 calls, IH-01 3, IH-02 3, IH-03 2, and both of IH-03's calls failed while their runs were marked Complete.

14 Oct 2026 · Day 2, morning

Four test flows, and a failed call that looks healthy

On a free developer instance the REST step was locked until I activated the Integration Hub installer plugin from the developer site. After that, I built four flows, each triggered by a new incident with a matching short description:

  • IH-00 no call: adds a work note. Control, 0 transactions expected.
  • IH-01 one call: one REST GET to a public test API.
  • IH-02 call before check: makes the call first, then only acts if the incident is priority 1.
  • IH-03 failing call: calls an address that always returns HTTP 500.

10 incidents produced 10 runs, all marked Complete. That includes both IH-03 runs, where the call returned 500. The action's "Don't Treat as Error" output is true by default, so a failing call doesn't fail the flow.

The outbound HTTP log has every call with its status code and time. Its source table is Step Instance, but at the default log level the Source record ID is empty, so the log knows a flow step made the call but not which one. Matching by time linked all 8 calls to their runs by hand.

13 Oct 2026 · Day 1

From 21 ideas to one, and a spike with kill rules

Scouted 21 ideas in four areas and dropped the ones ServiceNow already ships or that I couldn't test on a free instance. Picked Integration Hub transactions for its link to money and because the platform has its own ledger to check against.

Wrote the spike plan before touching the instance. It would stop if the REST step wasn't available for free, if the ledger still showed nothing 48 hours after the runs, or if the counts didn't match and one more round couldn't explain why. Prediction on record: 10 runs, 8 transactions.
